# 所有権とライフタイム

<!-- Japanese translation of rust-lang/nomicon at 5791ca9f5d671328af7a8fe87b42ca90c7211d28; prose modified. See ../README.md for attribution and licenses. -->

所有権は、Rust を際立たせる機能です。ガーベジコレクションを避けながら、Rust が完全なメモリ安全性と効率性を両立できるようにします。所有権システムの詳細に入る前に、この設計が必要とされる理由を考えてみましょう。

ガーベジコレクション（GC）は常に最適な解決策とは限らず、状況によってはメモリを手動で管理するのが望ましいこともある、という点は受け入れているものとします。そう思わないのであれば、別の言語はいかがでしょうか。

GC をどう評価するにせよ、コードを安全にするうえで、GC が*非常に大きな*恩恵をもたらすのは明らかです。データが*早すぎる*時点で消えてしまうことを心配する必要はありません（ただし、そのデータをまだ指し続けたかったかどうかは別問題ですが……）。これは、C や C++ のプログラムが広く対処しなければならない問題です。GC のない言語を使ったことがある人なら、誰もが一度は犯したことのある単純な間違いを考えてみましょう。

```rust,compile_fail
fn as_str(data: &u32) -> &str {
    // 文字列を計算する
    let s = format!("{}", data);

    // しまった！この関数の中でしか存在しないものへの
    // 参照を返してしまいました！
    // ダングリングポインタ！解放後使用！なんてことでしょう！
    // （これは Rust ではコンパイルできません）
    &s
}
```

まさにこの問題を解決するために、Rust の所有権システムは作られました。Rust は `&s` が存在するスコープを把握しているため、それがスコープ外へ逃げるのを防げます。しかし、これは C コンパイラでも検出できそうな単純な例です。コードが大きくなり、ポインタがさまざまな関数に渡されると、状況は複雑になります。やがて C コンパイラは、コードが不健全であると証明するのに十分なエスケープ解析を行えなくなります。その結果、プログラムが正しいという前提で受け入れるしかなくなります。

Rust では、これは決して起こりません。すべてが健全だとコンパイラに証明するのは、プログラマの責任です。

もちろん、所有権をめぐる Rust の仕組みは、参照が参照先のスコープから逃げないことを確かめるだけより、ずっと複雑です。ポインタが常に有効であることを保証するのは、それよりもはるかに難しいからです。たとえば、次のコードを見てください。

```rust,compile_fail
let mut data = vec![1, 2, 3];
// 内部への参照を取得する
let x = &data[0];

// しまった！`push` により `data` の格納領域が再割り当てされます。
// ダングリングポインタ！解放後使用！なんてことでしょう！
// （これは Rust ではコンパイルできません）
data.push(4);

println!("{}", x);
```

単純なスコープ解析では、このバグを防ぐには不十分です。`data` は、必要な期間だけ実際に存続しているからです。しかし、`data` への参照がある間に、`data` は*変更されました*。このため Rust は、参照が参照先とその所有者を凍結することを要求します。
